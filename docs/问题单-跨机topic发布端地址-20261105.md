# 问题单：跨机 topic 订阅收不到数据（发布端地址恒为 127.0.0.1）

| 项 | 内容 |
|---|---|
| 编号 | ISSUE-TOPIC-HOST-20261105 |
| 发现时间 | 2026-11-05 18:00 前后 |
| 现象 | PC 端订阅板端 `FaceResult` 永远收不到数据；PC 日志显示发布端为 `127.0.0.1` |
| 归属 | **框架缺陷**（OmniBinder），不是板端配置、不是网络、不是业务代码 |
| 上游状态 | **已修复**（commit `9dbdb49`，2026-09-27）；本地框架基线早于该提交 |
| 影响 | 所有**跨机 topic 订阅**；板内订阅（SHM）与跨机 RPC 不受影响 |
| 处置 | 将框架对齐到上游该提交，重建 `libomnibinder.a` → 重编 app → 部署重启 |

---

## 1. 现象与证据

### 1.1 PC 端（客户端）

```
[I][OmniRuntimeSM]  Topic FaceResult publisher at 127.0.0.1:36339
[I][TcpClientTransport] Connected to 127.0.0.1:36339 (fd=10652)
[W][TcpClientTransport] sendAll() incomplete on fd=10652: bytes=34 timeout_ms=0
[W][ConnMgr]            data_send_incomplete service=FaceService transport=TCP
[W][OmniRuntimeConnection] topic_subscribe_send_failed topic=FaceResult publisher=FaceService
[W][OmniRuntimeSM]      Failed to establish topic publisher path for FaceResult
```

客户端拿到的发布端地址是 `127.0.0.1:36339` —— 它连接的是**自己**，因此数据面握手必然失败，一帧数据都收不到。

同一台 PC 上，`lookupService("FaceService")` 是成功的，说明**控制面通、数据面地址错**。

### 1.2 板端（发布方）

三项检查全部通过：

```
# ① 进程环境
FACE_REGISTER_HOST=192.168.10.168

# ② 部署的二进制含 D2 代码（对比有无该字符串即可判断是否重编过）
grep -ac "advertise host" /root/nfs/3516-media-refactor/dist/hi3516/bin/face_proc
1

# ③ 运行时日志
[face] advertise host=192.168.10.168 (env FACE_REGISTER_HOST=set)
```

即：**板端已经把 register host 设对了、也确实生效了**，但 PC 看到的仍是回环地址。

### 1.3 结论

`setRegisterHost` 只作用于 **service 注册**，**没有作用于 topic 发布端**。两条代码路径不一致。

---

## 2. 根因（代码级）

框架里"对外通告地址"有三个使用点，只有前两个走了地址解析链：

| 使用点 | 代码位置（本地版本） | 实际行为 |
|---|---|---|
| service 注册 | `src/core/runtime_service.cpp:79` → `resolveRegisterHost(service, listenerAdvertiseHost())` | ✅ 得到板 IP |
| **topic 首次发布** | **`src/core/runtime_topic.cpp:132`** → `pub_info.host = listenerAdvertiseHost()` | ❌ 恒为 127.0.0.1 |
| **topic SM 重连恢复** | **`src/core/runtime_sm.cpp:434`** → `pub_info.host = listenerAdvertiseHost()` | ❌ 恒为 127.0.0.1 |

而 `listenerAdvertiseHost()` 的实现是写死的（`runtime_service.cpp:88-93`）：

```cpp
std::string OmniRuntime::Impl::listenerAdvertiseHost() const {
    // core 固定以 0.0.0.0 绑定 TCP 监听……
    return normalizeAdvertiseHost("0.0.0.0");   // → "127.0.0.1"
}
```

所以只要这两处直接调用它，**无论 `setRegisterHost` 设什么，跨机 topic 都不可用**。

---

## 3. 已排除项（避免重复排查）

以下都已被实测排除，**不要再从这些方向查**：

| 假设 | 排除依据 |
|---|---|
| 板端没设 `FACE_REGISTER_HOST` | `/proc/<pid>/environ` 里有该变量 |
| 板端二进制太旧（无 D2） | 二进制含 `advertise host` 字符串，日志也打印了 |
| 网络不通 | 板端 554/9900 均可达；同一台 PC 用 ffmpeg CLI 连读 15 秒正常 |
| RTSP 并发上限 | ffplay 占用时另开一路 CLI 仍正常 |
| 解码器/编码不兼容 | 本地 mp4 可播；H.264/HEVC 直播在修复 seek 问题后均可播 |
| `sm_host` 传错 | 客户端 `init()` 传的是板 IP `192.168.10.168`，SM 连接成功 |
| PC 侧端口转发可绕过 | 实测框架那条 TCP 连接没有落到转发监听上，方案无效 |
| 改 `rt_.init("板IP", 9900)` 可绕过 | `listenerAdvertiseHost()` 写死 `"0.0.0.0"`，与 init 参数无关 |
| 只加 Service 级 `fsvc_.setRegisterHost()` 可绕过 | topic 路径根本不读 service 的 register host |

## 5. 处置方案

### 方案 A1：最小对齐（只修地址）

只取 `9dbdb49` 中 `runtime_topic.cpp`、`runtime_sm.cpp` 的两处 hunk。

- 改动：2 行 + 注释
- 风险：极低；未设 register host 的进程行为完全不变（`resolveRegisterHost` 会回落 `normalizeAdvertiseHost(listener)`）
- 缺点：`sendAll incomplete`（半帧）等同类缺陷仍在

### 方案 A2：整提交对齐（推荐）

```bash
git fetch origin
git cherry-pick -n 9dbdb49973c9885004f3292b674c10d4f5d12a0f
```

- 收益：地址问题 + 数据面半帧 + 回调 UAF + 诊断顺序等一并修复
- 风险：该提交跨 `core/transport/tests`，本地基线较早（09-12），**可能出现冲突**
- 处理原则：冲突时以"语义"为准，不要机械取一边；涉及本地已有改动（如 D4 advertise 日志 `110934c`）时保留本地提交

> 若 cherry-pick 冲突过多，退化为 A1 + 单独取"数据面半帧"那一段，其余留待基线升级。
